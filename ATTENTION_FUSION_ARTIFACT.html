First principle

Attention = 按当前问题，动态读取一组信息

Camera encoder 把图像切成 patch tokens；LiDAR encoder 把点聚合成 voxel tokens。Attention 不直接比较 RGB 与 XYZ，而是比较它们经过学习投影后的向量。

image patches → C = {c₁, c₂, ...}
LiDAR voxels → L = {l₁, l₂, ...}

scoreᵢ = (Wq·c) · (Wk·lᵢ) / √d
α = softmax(score)
output = Σ αᵢ · (Wv·lᵢ)
“匹配”不是必须选中唯一 LiDAR voxel。一个视觉车体 token 可以同时读取车头、车门和车尾的几何 feature，只是权重不同。
几何标定仍然重要：通常先用内外参构造候选邻域，再让 attention 在候选中做软匹配。Transformer 不是用来取代 calibration 的。
Mental model

Q 是问题，K 是可匹配的地址，V 是真正取回的内容

K 与 V 通常来自同一组 tokens，但作用不同：K 用来算相关性，V 才是最终被加权汇总的信息。

Q

Query · 当前需求

由“正在被更新的 token”生成。Camera voxel 做 Q 时，它在询问：哪些 LiDAR 几何与我的视觉假设相关？

像搜索框里输入的查询语句。
K

Key · 匹配地址

每个 LiDAR voxel 提供一个可比较的索引向量，决定自己是否应该被当前 Camera query 读取。

像数据库中供搜索的索引。
V

Value · 返回内容

真正被聚合的 LiDAR 内容：距离、局部表面、稀疏形状与强度等编码后的 feature。

像检索结果中返回的正文。
① 相似度Camera query 与每个候选 LiDAR key 点积，得到一排相关性分数。
→
② 归一化softmax 把分数变成总和为 1 的读取权重。
→
③ 检索根据权重汇总 LiDAR values，得到几何 update。
The crucial detail

Q 的来源决定输出数量和坐标锚点

Q = Camera每个输出仍对应一个 Camera token / camera-lifted voxel。
Q = LiDAR每个输出仍对应一个非空 LiDAR voxel 或 LiDAR proposal。
Q = Entity每个输出对应一个 object/entity hypothesis，而不是规则 voxel。
但 Q 来自谁，并不单独决定主导权。还要看输出加回谁的 residual、后续 head 读取谁、另一模态能否单独创建 token。
Fout = Camera residual
      + gate · CrossAttn(C, L, L)

上式才是明确的 Camera-dominant block：输出 token 属于 Camera 流，LiDAR 只是增量。

Two common confusions

Self / Cross 与 Single / Multi-head 是两组不同概念

Self-attnQ、K、V 来自同一 token 集合，例如 Camera↔Camera。
Cross-attnQ 来自一组 tokens，K/V 来自另一组，例如 Camera→LiDAR。
Multi-head并行使用多组 Wq/Wk/Wv，在不同特征子空间计算 attention。
不同 head 没有人为规定一定负责“深度”或“边界”；这里是直觉解释。实际训练中这些职责是涌现、重叠的。
headₕ = Attn(CWqₕ, LWkₕ, LWvₕ)
ΔL = Concat(head₁,...,headₕ) · Wo

点击左侧不同 head，理解同一对 Camera/LiDAR tokens 可以在多个关系子空间中被同时匹配。

Proposed architecture

Camera 决定“像不像一个物体”，LiDAR 帮它落到正确的 3D 空间

Why two feature streams?

不是所有输出都该读取同一个 fully-fused feature

OOD / class优先读取 Camera semantic state 与 visual entity embedding。
3D mask读取 Camera + LiDAR 的 fused geometry，保证距离和边界准确。
occupancyvoxel-wise 保留精细空间状态；entity-wise 保持物体整体一致性。
Entity query 先从 Camera 建立，避免系统只能在 LiDAR 非空 voxel 上产生物体 proposal。
LiDAR 不是被忽略，而是从“决定物体是什么”转为“校准它在哪里、占据哪些空间”。
q_sem = EntityAttn(q, C′)
q_geo = GeoAttn(q_sem, Fgeo)
OOD = Head(q_sem)
Mask = q_geo · VoxelMaskFeat
Architecture decision

三种设计都合理，但它们回答的是不同任务假设

推荐给 OOD Occupancy

Camera-dominant

视觉建立 dense voxel/entity hypothesis，LiDAR 作为几何 memory。

  • 长尾和 OOD 外观保留得最好
  • 无 LiDAR 点处仍有视觉状态
  • 需要谨慎处理 Camera 深度歧义

LiDAR-dominant

非空 LiDAR voxel 或 proposal 主动读取图像语义。

  • 几何非常稳
  • 计算天然稀疏
  • 容易受 LiDAR token coverage 限制

Bidirectional / Equal

两个流彼此更新，或投到统一 token space 后联合 self-attention。

  • 表达能力强、适合通用感知
  • 模态互补充分
  • 可能冲淡 OOD 所需的视觉语义来源

Four tests for “who dominates?”

不要只看 Q 来自谁

1Query ownership：谁发起信息检索？
2Residual ownership：attention update 最终加回谁？
3Token birth：某一模态缺失时，谁仍能创建 voxel/entity token？
4Head routing：objectness、semantic、OOD 和 mask 分别读取哪条 feature stream？
一句话：Attention 只是“谁向谁读取信息”；整个网络的主导权，是由状态保存和任务 head 的信息路径共同定义的。
